> 文档状态：v2 实现与验收合同
>
> 更新日期：2026-08-08
>
> 原始需求：[旅行饼狗开发纲要](specs/旅行饼狗开发纲要.md)
>
> 固定路径：`https://emmm1e3m.github.io/AllForSUXINHAO/TravellingBingo/`

## 1. 产品定义

“旅行饼狗”是一款以饼狗为主角的离线收集网页游戏。产品的核心不是不断点击抽取，而是在一个有生活感的房间里陪饼狗完成日常、尊重它当下的意愿，然后在旅行、刷播与冲热中收集回忆。

产品原则：

- 房间是主体，面板是辅助；玩家通过房间和饼狗进入行动。
- 苹果有清楚的获得与花费路径，同一个流程不同时消耗和返还苹果。
- 饼狗不是无条件执行指令的按钮；它有偏好、疲劳和休息周期。
- 收藏以“第一次看见”为惊喜，不在开局暴露所有分类和空位。
- UI 文案只描述饼狗的世界和当前行动，不在游玩界面讲解系统实现。
- 明信片、百万直拍与全站第一都使用已授权的真实素材；生成式图像只用于房间和饼狗角色。

## 2. 运行与发布边界

- 游戏不需要账号、游戏后端、排行榜、真实支付、广告或用户跟踪。
- `.bingo` 是玩家可下载和再导入的唯一权威存档形式；PWA 缓存不是存档。
- 首次在线访问并缓存应用外壳后，标题页、房间、计时、领奖、导入与导出应可离线工作。未访问过的高清收藏图不承诺离线可用。
- GitHub Pages 根首页仅提供进入按钮。游戏源码、PWA `scope`、manifest `id/start_url`和 Vite `base` 全部固定为 `/AllForSUXINHAO/TravellingBingo/`。
- `AllForSUXINHAO/` 只放置 `TravellingBingo/`。Pages 仅上传组装后的 `_site/`，不公开 `docs/`、`research/`、`resources/raw/`、源码或下载脚本。

## 3. 信息架构与主流程

```text
根首页入口
  → 标题页
  → 开始新旅程 / 选择 .bingo
  → 存档摘要确认
  → 饼狗的房间
      ├→ 点饼狗 → 行动菜单
      ├→ 点房间区域 → 走路 → 对应互动
      ├→ 完成三条 Bingo 任务 → 获得苹果 → 刷新任务板
      ├→ 向冰箱中补充道具
      ├→ 旅行 / 刷播 / 冲热 → 112 秒 → 领取结果
      ├→ 床铺休息 → 日夜转场 → 刷新偏好
      ├→ 饼狗的收藏墙
      └→ 奇迹饼狗 → 新窗口舞台测试
  → 离开房间
  → 下载最新 .bingo
  → 返回标题页
```

## 4. 标题页

标题页是一张安静、清晰的旅程邀请，不是开发信息看板。

### 4.1 首屏内容

- 短标题“旅行饼狗”。
- 一句有情境感的短引导，不重复功能说明。
- 主操作“开始新旅程”。
- 次操作“读取 `.bingo`”。
- 非官方、非商业粉丝作品声明位于低干扰的页脚区域。

首屏不陈列内部版本号、存档技术、调试状态、人物长段定位或完整玩法教程。

### 4.2 存档导入

- 文件选择后先校验，不立即覆盖当前状态。
- 预览只显示对玩家有用的摘要：导出时间、苹果、饼狗当前状态与是否有进行中活动。
- 文件名和错误文本始终以纯文本渲染。
- 只有点击“进入这次旅程”后才采用已校验存档。

### 4.3 DEBUG 入口

标题连续激活五次后仍可触发隐藏 DEBUG 入口，但调试能力不在普通首屏展示。密码只是隐藏交互，不是安全边界。

## 5. 视觉系统

### 5.1 字体

| 用途 | 字体 | 公开文件 |
|---|---|---|
| 游戏标题、页面大标、数字强调 | 可画乐融融 | `assets/fonts/kehua-lerongrong.woff2` |
| 按钮、任务、卡片、辅助信息 | 可画奶糖体 | `assets/fonts/kehua-naitang.woff2` |

源字体位于 `resources/raw/travelling-bingo/fonts/`。构建仅将项目实际使用的字符转换为 WOFF2 子集，并在 CSS 中提供合理的本地回退字体。按钮和正文不应用过度粗重的标题字。

### 5.2 配色与材质

```text
奶油背景    #FFF4E4
暖象牙面板  #F9E8CF
苹果红主色  #C43B4A
柔杏色强调  #E8A08A
栗棕正文    #5C3B33
蜂蜜金提示  #D7A044
浅粉桃装饰  #F3C7BD
```

绿色只作为少量植物和饼狗头顶小芽的自然点缀，不担任面板、按钮或完成态的主色。边框、阴影和按钮使用轻量纸张层次，不使用厚重黑边和多层硬阴影。

上述 token 用于网页 UI，不是重绘房间母版的指令。房间必须保留用户 `image-1` 的原有色彩关系、手绘质感和细节，只做忠实的高清修复。

### 5.3 按钮

- 房间热点使用“床铺”、“电脑”、“冰箱”、“房门”等文字，不用抽象图标要求玩家猜测。
- 所有主交互的触控目标至少 `44 × 44 CSS px`。
- 主、次、文本三种按钮必须共用统一的圆角、内边距、焦点圈和按压反馈。
- 不使用原生 `<select>`；短选项用分段文字按钮，概率调节用可键盘操作的滑杆与数字回显。

## 6. 房间布局与角色移动

### 6.1 桌面布局

- 顶栏、房间舞台和右侧信息卡共用同一页面网格。
- 房间舞台和右侧信息卡在同一行顶部对齐，不再使用垂直居中把房间压到下方。
- 房间舞台固定使用 `1098 / 1433` 竖版比例，响应式等比缩放。图像不改变构图方向、不拉伸，也不裁掉人物、兔子装饰、树冠或交互家具。
- 饼狗的 CSS 尺寸不随背景放大；用相对百分比锚点改变位置。

### 6.2 手机布局

- 顶栏收紧为必要操作，房间先于任务卡展示。
- 房间热点不能在窄屏直接消失；可以缩短文字、用上下文分组或收入饼狗菜单。
- 任务板、补给和收藏使用底部抽屉或全屏对话框，内容区独立滚动，关闭按钮固定可达。

### 6.3 房间素材

房间只有一个生产母版：

```text
resources/raw/travelling-bingo/generated/chan-chan-house-v2.png
```

网页派生图为：

```text
public/assets/game/chan-chan-house-v2-768.webp    # 768 × 1002
public/assets/game/chan-chan-house-v2-1098.webp   # 1098 × 1433
```

该母版以用户提供的 `resources/raw/travelling-bingo/references/outline/image-1.png`（509 × 665）为唯一构图参考，使用 ImageGen `precise-object-edit` 直接做高清修复。它必须严格保留原竖版构图、绘画风格、两层结构、树冠边界、人物、兔子装饰、床铺、电脑、衣架、电子琴、唱片机、冰箱、收藏墙和房门的位置与相对关系。只允许提升清晰度、边缘稳定性和细小纹理，不生成另一种构图或重新摆放物件。

### 6.4 饼狗移动与状态

- 点击房间文字热点后，饼狗先使用走路帧移动到目标锚点，到达后切换为对应动作。
- 饼狗本身是可聚焦按钮；点击或按 Enter/Space 展开当前可用行动、偏好和进行中状态。
- 饼狗位于某区域或正在那里工作时，该区域热点不渲染，避免按钮遮挡饼狗。
- 旅行的 `outside` 状态完全不渲染饼狗 DOM，不仅是设置透明度。
- 行动母版使用 `bingo-actions-v2.png`与 `bingo-walk-v2.png`；网页使用透明 WebP 帧带。CSS 动画必须保持脚底基线和角色尺寸稳定。

## 7. 持久领域状态

v2 将会影响游戏结果的数据集中到领域层。下列为概念结构，精确名称以 TypeScript 实现为准：

```ts
interface GameStateV2 {
  schemaVersion: 2
  profile: {
    createdAt: number
    debug: boolean
  }
  economy: {
    apples: number
  }
  inventory: Inventory
  collections: Record<string, CollectionEntry>
  activeActivity: ActivityRun | null
  pet: {
    location: PetLocation
    day: number
    preferenceCycle: number
    preferences: Record<ActivityKind, ActivityPreference>
    lastRestedAt: number | null
  }
  taskBoard: {
    cycle: number
    tasks: readonly [TaskInstance, TaskInstance, TaskInstance]
    recentTemplateIds: string[]
  }
  debugTuning: DebugTuning | null
  statistics: GameStatistics
  random: {
    seed: string
    activitySequence: number
    taskSequence: number
    preferenceSequence: number
  }
}
```

收藏目录是当前版本的运行时输入，不是 `GameStateV2` 的一部分：

```ts
interface CollectionCatalog {
  postcard: readonly string[]
  'million-shot': readonly string[]
  'site-first': readonly string[]
  siteFirstChronology: readonly string[] // 旧 → 新
}
```

`.bingo` 中的收藏推进只依赖 `collections` 的已拥有 ID 集合，首获时间只用于展示排序。存档不保存：

- 当前目录的分类总数或总收藏数；
- 全站第一的“下一项”索引或指针；
- `unlockedCategories` 或等价的分类解锁列表。

总数、完成度、下一个全站第一和已解锁分类全部由“当前目录 + 已拥有 ID 集合”即时派生。因此目录日后追加新 ID 时，旧存档不需要改 schema 或重置进度，新 ID 会自然进入未拥有集合。

当前打开哪个抽屉、动画播到哪一帧、对话框焦点和日夜转场进度都是 UI 状态，不写入 `.bingo`。

### 7.1 随机序列分离

活动奖励、任务刷新和偏好生成使用同一个存档 seed 派生的三条独立序列。睡觉或刷新任务不能改变下一次收藏掉落。失败的领域动作不推进任何随机序列。

## 8. Bingo 任务板

### 8.1 刷新规则

- 新游戏和老存档迁移后都生成恰好三条任务。
- 同一板不重复任务模板，尽量不重复触发组，并排除当前无法完成的条件任务。
- 每条任务完成时立即写入完成时间并发放苹果，不需要再点“领取”。
- 三条都完成时，产生一次 `Bingo!` 效果，领域层立即生成新板，UI 可延迟约 0.8 秒显示以完成动画。
- 触发旧板完成的那个事件不再推进新板。
- 任务实例保存目标和奖励快照，以后调整任务库时不改变已签发任务。

### 8.2 任务库基线

| 类别 | 示例任务 | 完成条件 | 苹果 |
|---|---|---|---:|
| 陪伴 | 和饼狗打个招呼 | 点击饼狗一次 | 1 |
| 陪伴 | 看看饼狗的小背包 | 打开饼狗菜单 | 1 |
| 移动 | 陪饼狗去两个不同角落 | 到达两个不同区域 | 2 |
| 音乐 | 陪饼狗弹一会儿琴 | 互动电子琴 | 1 |
| 音乐 | 和饼狗听一张唱片 | 互动唱片机 | 1 |
| 音乐 | 听完房间里的两种声音 | 分别互动两种乐器 | 2 |
| 换装 | 帮饼狗挑一身装扮 | 互动衣架 | 1 |
| 回忆 | 去看看饼狗的收藏 | 有收藏时打开收藏墙 | 1 |
| 回忆 | 重温两份不同的回忆 | 查看两项不同收藏 | 2 |
| 奇迹 | 测试什么样的舞台适合你 | 打开舞台测试，每档仅一次 | 3 |

任务库可继续扩展，但不接入“购买补给”、“启动活动”、“领奖”等苹果或道具消耗事件。

## 9. 苹果经济与冰箱

### 9.1 单向经济

```text
无消耗的 Bingo 小任务 → 苹果
苹果 → 向冰箱中补充道具
道具 → 旅行 / 刷播 / 冲热
活动 → 收藏或朋友事件
```

禁止以下流向：

- 活动基础奖励苹果；
- 旅行便当附加返还苹果；
- 任何收藏结果兑换苹果；
- 朋友事件赠送苹果；
- 购买、活动、领奖进度任务。

### 9.2 补给基线

| 补给 | 基线花费 | 用途 |
|---|---:|---|
| 普通旅行便当 | 3 | 启动一次旅行 |
| 苹果旅行便当 | 5 | 启动旅行，并使当次遇见朋友概率增加 15 个百分点，封顶 100% |
| 信号耳机 | 4 | 启动一次刷播 |
| 热度工具箱 | 7 | 启动一次冲热 |
| 幸运苹果 | 6 | 使当次活动对应收藏掉落概率增加 20 个百分点，封顶 100% |

幸运苹果只在基础收藏掉落概率低于 100% 且对应分类尚未集齐时可用；否则入口不可选择，尝试使用也不扣除幸运苹果。初始苹果和最终价格从统一调参文件读取，基础概率与两项单次加成从 `gameBalance` 模块读取，不在 UI 组件内重复硬编码。界面用语为“向冰箱中补充道具”或更简短的世界内文案。

## 10. 活动、计时与结果

### 10.1 三类活动

| 活动 | 房间入口 | 饼狗位置 | 主收藏 |
|---|---|---|---|
| 旅行 | 房门 | `outside`，房间不显示 | 明信片 |
| 刷播 | 电脑 | 电脑前 | 百万直拍 |
| 冲热 | 电脑 | 电脑前 | 全站第一 |

开始活动的检查顺序：

1. 当前是否有其他进行中活动；
2. 饼狗对该活动的偏好是否允许；
3. 库存是否有所需补给；
4. 参数与时间是否合法；
5. 在同一个 reducer 变更中扣道具、预先生成奖励计划并写入结束时间。

任一检查失败时保持状态、库存与随机序列不变。

### 10.2 绝对时间

```ts
DEFAULT_ACTIVITY_DURATION_MS = 112_000
```

- `endsAt - 1 ms` 仍是进行中；`endsAt` 起可领取。
- `activeActivity.startedAt` 与 `activeActivity.endsAt` 必须原样写入 `.bingo`；读档继续按存档内的原 `endsAt` 判断完成，不按当前默认时长重算。后续增加默认时长只影响新开始的活动。
- 页面每秒刷新视图，并在 `focus` 和 `visibilitychange` 后立即重算。
- 不用长时间 `setTimeout` 作为权威计时器。
- 活动开始时就写入完整 `rewardPlan`；导出、导入或修改 DEBUG 概率后不重抽已开始的活动。
- 领奖必须携带当前 `runId`，只在它与进行中活动匹配且时间已到时原子发放，避免双击重复领取。

### 10.3 结果文案

- 全站第一命中：“全站第一！”
- 全站第一未命中：“很遗憾没能拿到全站第一”
- 刷播未掉落时描述本次陪伴或当下状态，不把海报写成每次活动的唯一目标。
- 旅行结束、刷播结束与冲热结束分别有自己的标题，不用同一句模板概括。
- 一般收藏按钮为“收进收藏墙”；首次获得某分类时额外告知分类解锁。已拥有 ID 不在后续掉落候选中。

## 11. 活动偏好与睡眠

### 11.1 偏好生成

每个清醒周期为三种活动生成偏好。基线分布：

| 拒绝数量 | 概率 |
|---|---:|
| 0 种 | 35% |
| 1 种 | 50% |
| 2 种 | 15% |

生成后永远至少保留一种可执行活动。活动领取后，对应偏好进入疲劳状态。

### 11.2 拒绝反馈

- 拒绝文案表现“现在不想做”或“有点累”，不将饼狗写成错误或惩罚对象。
- 显示耷耳、困倦或轻轻摇头的拒绝动作。
- 提示玩家去床铺休息，但不自动代替玩家执行。

### 11.3 床铺休息

- 只有当 `activeActivity === null` 时允许。
- 不花费苹果，不发放苹果，不推进任务。
- 增加日数与偏好周期，清除疲劳并生成新偏好。
- reducer 返回一次性 `pet-rested` 效果，视图播放约 2.4 秒的变暗—夜色—重新亮起。
- 转场层应当覆盖整个场景而不只是饼狗，不需要另一张夜间房间图。
- `prefers-reduced-motion` 下缩短为柔和的明暗切换，不使用闪烁。

## 12. 统一概率配置与 DEBUG

时长、基础掉落、朋友相遇、偏好分布、补给的单次概率加成和道具价格必须从领域层的统一调参源导出；其中基础概率与两项单次加成集中在 `gameBalance` 模块，不得散落在组件和奖励函数中。推荐基线：

```ts
export const LUCKY_APPLE_COLLECTION_DROP_BONUS = 0.20
export const APPLE_LUNCHBOX_FRIEND_BONUS = 0.15

export const DEFAULT_GAME_BALANCE = {
  activityDurationMs: 112_000,
  probabilities: {
    postcard: 1,
    millionShot: 0.4,
    siteFirst: 0.1,
    friend: 0.2,
  },
} as const
```

规则：

- 全站第一基础命中概率严格为 10%，不设置额外保底；默认配置下使用幸运苹果后，当次概率为 30%。
- 单次加成统一按 `Math.min(1, base + bonus)` 计算，是增加百分点，不是乘权重或相对增长；幸运苹果加 `0.20`，苹果旅行便当加 `0.15`。
- 基础收藏掉落概率已为 `1` 或对应分类已集齐时，幸运苹果不可使用且库存不变。
- 判定统一为 `roll < chance`；`0` 永不命中，`1` 必定命中。
- DEBUG 用数字滑杆调整明信片、百万直拍、全站第一与朋友相遇概率，并显示百分比。
- 不维护预制的全收集存档；DEBUG 保留“一键全收集”按钮，由当前收藏目录即时生成调试状态，并保留立即完成、增加苹果与备份导出。危险操作使用项目内确认对话框，不调用浏览器 `confirm()`。
- 正常存档不允许伪造非空 DEBUG 覆盖。

## 13. 饼狗的收藏墙

### 13.1 数据口径

- 12 张明信片全部来自用户指定的 [Bilibili Toy 活动页](https://www.bilibili.com/toy/preview/preview_5SdX8Yet/index.htm) 对应归档。
- 30 张百万直拍使用已锁定的微博海报及 SHA-256 清单。
- 8 项全站第一使用已核验的设计海报或指定视频封面。
- 游戏运行时不跨域请求微博或 B 站图片，只读取同源 WebP 和 JSON 目录。

### 13.2 不重复的获得规则

- 每次活动开始时先对应类别做掉落概率判定；未命中时不选收藏。
- 明信片命中后，计算 `catalog.postcard - ownedIds`，再用存档随机序列在剩余集合中等概率选一项。
- 百万直拍命中后，计算 `catalog['million-shot'] - ownedIds`，再在剩余集合中随机选一项。
- 全站第一命中后，不乱序；从 `siteFirstChronology` 头部开始找第一个未拥有 ID。
- 当前全站第一序列为 Dynamite → Talk WORTHY? Talk DIRTY! → Make A Wish → Dawn in my soul → 愿与愁 → 囍 → Hey Mama → POWER，按从旧到新获得。
- 任一类别的剩余集合为空时，该类别不再产生收藏，不会再次返回已拥有 ID。
- 奖励 ID 在活动开始时写入 `rewardPlan`，导出、导入或目录顺序变动都不重抽已开始活动。

全站第一目录 schema 必须验证：

- `chronology` 是从 1 开始且无缺口、无重号的连续正整数；
- chronology 中的 ID 集合与全站第一目录 ID 集合完全相同；
- 首项是 Dynamite。

POWER 只是当前目录的最新项，不是通用 schema 的永久终点。新的全站第一可在它之后按下一个 `chronology` 追加，不需要修改 schema 或旧存档。

### 13.3 解锁和排序

- 没有收藏时只显示温和空状态，不显示分类标签。
- 某一类第一次获得时才显示该分类，并播放一次解锁反馈。
- 只渲染已获得卡片，不构造问号、灰色卡或空槽。
- 全部已获得卡片按 `firstObtainedAt` 从新到旧排序，时间相同时按 ID 稳定排序。
- 未全部集齐时，HUD、标题、分类标签和空状态都不显示总数或百分比。全部集齐后才显示完成数并触发总收集庆祝。
- 海报缩略图容器固定比例，使用 `object-fit: cover`；放大查看时可以使用 `contain`。
- 右上角收藏入口显示 `🖼️`，有可读的 `aria-label` 和文字提示。

## 15. `.bingo` 存档与迁移

### 15.1 外层格式

- UTF-8 JSON，扩展名 `.bingo`，MIME `application/octet-stream`。
- 包含格式标识、导出时间、游戏 payload 和 SHA-256 完整性摘要。
- 最大 1 MiB，Zod 严格校验，未知顶层字段拒绝。
- 先根据原始 payload 验证摘要，再执行版本迁移，不得先修改内容再验签。

SHA-256 只用于发现损坏和手误，不是密钥签名，不承诺防止玩家主动修改。

### 15.2 v1 到 v2

- 保留苹果余额、现有库存、收藏、首次获得时间、seed 和可恢复的进行中活动。
- 旧随机序号迁移为活动序号；任务与偏好使用 seed 派生的独立序列，不消耗活动随机数。
- 为迁移后存档生成三条可完成任务和一组确定偏好。
- 历史统计可放入明确的 legacy 字段，但 v2 新活动不继续产生旧经济流。
- 若旧存档有进行中活动，保留结束时间、未拥有的计划收藏与朋友结果，将旧活动计划中的苹果收入清零，并仅在 v1 → v2 迁移时返还已扣的活动补给和幸运苹果。
- 新导出只写 v2；v2 重新导入不会再次返还旧活动补给。
- 存档不写入当前目录总数、全站第一下一索引或分类解锁列表。导入时用当前目录校验已拥有 ID；目录只增加新 ID 时，旧存档继续有效，新 ID 自然可获得。

### 15.3 导出

- 普通文件名：`travelling-bingo-YYYYMMDD-HHmmss.bingo`。
- DEBUG 存档在扩展名前附加 `-debug`。
- 有未导出更改时注册 `beforeunload` 提示；浏览器关闭事件不承诺自动下载。
- “离开饼狗的房间”是可靠导出路径：先下载存档，再返回标题页。

## 19. PWA、性能与缓存

- App Shell、字体子集、小尺寸房间和收藏缩略图进入合理的预缓存范围。
- 高清收藏图按需缓存，不把整个收藏库压入首次加载。
- 固定文件名的图像需要内容 revision 或版本化 URL，不使用无期限的旧图缓存。
- 预缓存清单不允许重复 URL，站点校验需要检查唯一性、白名单边界与实际文件数。
- 新 Service Worker 可用时提示玩家更新，不在未导出变更时自动刷新。

| 初始预缓存 | ≤ 5 MiB |

## 20. 安全、隐私与可访问性

- 不加入统计、跟踪、指纹或第三方广告脚本。
- GitHub PAT、微博 Cookie、浏览器登录态与抓取头不进仓库、构建产物或文档。
- 外链使用 `noopener noreferrer`；弹窗失败时提供安全备用链接。
- 导入对象通过 schema 重建白名单字段，不将不可信文本传给 `innerHTML`。
- 对话框打开时移入焦点、限定焦点、Escape 关闭并隔离背景；关闭后恢复到触发按钮。
- 奖励对话框关闭后焦点回到可用的房间入口，不回到已消失元素。
- 对话框背景点击同时支持指针和触摸事件，不只依赖鼠标。
- 颜色不是任务完成、偏好拒绝或新分类解锁的唯一信息。
- 所有动画遵循 `prefers-reduced-motion`；不自动播放有声音的内容。

## 22. 验收清单

### 22.1 领域与概率

- 新游戏生成恰好三条可完成任务，模板不重复。
- 单条完成立即奖励苹果；三条完成后换新板，不多发一次整板苹果。
- 旧板最后一次事件不推进新板。
- 购买、启动、领奖和被拒绝动作不推进任务。
- 活动命中、未命中和朋友事件都不改变苹果；收藏选择始终排除已拥有 ID。
- 拒绝活动时状态对象、库存和随机序号不变。
- 睡眠在忙碌时失败，空闲时重置偏好且苹果不变。
- 偏好生成始终保留至少一种可执行活动。
- 默认时长严格为 112 秒，边界前 1 ms 与边界时刻判定正确。
- 全站第一随机值 `0.099999` 命中，`0.1` 不命中。
- 朋友事件在默认配置下对 `0.199999` 命中，`0.2` 不命中。
- 幸运苹果将当次收藏概率增加 `0.20`，苹果旅行便当将当次遇友概率增加 `0.15`，加成结果均封顶 `1`。
- 基础收藏概率为 `1` 或对应分类已集齐时，幸运苹果操作失败且不扣库存。
- DEBUG 的 0% 与 100% 能稳定制造未命中与命中，且不改变已开始活动。

### 22.2 房间与交互

- 桌面房间与右侧卡片顶边对齐，房间尺寸比首版更大。
- 房间使用 1098 × 1433 竖版比例，和用户 `image-1` 重合对比时构图、两层结构、人物、兔子装饰和家具位置不漂移。
- 公开房间图恰好为 768 × 1002 和 1098 × 1433 两档，均可解码且与清单 SHA-256 一致。
- 家具热点是文字按钮，焦点可见，手机不丢功能。
- 饼狗走向热点锚点，到达后切换相应动作，当前热点隐藏。
- 点击饼狗或使用键盘可展开菜单，菜单告知可做、拒绝和疲劳状态。
- 旅行进行中和待领取时没有饼狗 DOM；刷播与冲热时电脑热点不存在。
- 睡眠播放整场景日夜转场，reduced-motion 无闪烁。
- 页面不存在原生业务下拉框。
- 奇迹饼狗在新窗口打开正确 URL，拦截弹窗时显示可聚焦备用链接。

### 22.3 收藏与图像

- 无收藏时不显示三个分类、总数、百分比或灰色卡。
- 首获分类触发一次解锁，后续奖励候选不包含已拥有 ID。
- 明信片和百万直拍在未拥有集合中随机选取，直到各自当前目录耗尽也不会再次返回旧 ID。
- 全站第一按 chronology 严格从 Dynamite 由旧到新，当前第八项为 POWER。
- 在 POWER 之后追加第九项的测试目录能通过通用 schema，无需修改代码中的末项常量。
- 收藏只显示已获得项，严格按首获时间降序。
- 未全收集时全页不存在总数进度，全收集后才显示完成状态。
- 列表海报铺满裁切，大图查看不破坏原图比例。
- 12 张明信片全部可追溯到 Bilibili Toy 归档，没有生成或占位图。
- 所有公开图片能解码、路径存在、有中文替代文本，素材锁校验通过。

### 22.4 存档、构建与上线

- v1 存档先校验再迁移，余额、库存、收藏与活动结果保留；进行中旧活动的已扣补给只在 v1 → v2 时返还一次。
- v2 导出再导入后，任务、偏好、概率覆盖、进行中活动与随机序号等价。
- 导出 JSON 不含收藏目录总数、全站第一下一索引或 `unlockedCategories`。
- 在三类目录中追加新 ID 后，旧 v2 存档仍能导入，新 ID 自动进入可获得集合。
- 损坏、超大、未知字段、摘要不符和未支持版本不修改当前游戏。
- `npm run verify`、生产构建、站点组装、公开边界验证和桌面/手机 E2E 全部通过。
- `_site/AllForSUXINHAO/` 仅有 `TravellingBingo/`，不包含原图、字体源、研究数据、测试报告或 sourcemap。
- 工作流与 Pages 部署成功后，根入口和游戏路径返回 200，首屏无控制台错误。

## 23. 交付完成标准

5. 工作区没有散落原图和可重建报告，分支、提交、PR、Pages 与线上路径均已验证。
